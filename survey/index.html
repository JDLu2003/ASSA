Agent as a Service
托管智能体服务的结构、现状与已有研究

2026 年，OpenAI、Anthropic、Google、AWS 和 Microsoft 都推出了以 agent 为调用对象的云服务：应用通过 API 提交任务、接收事件流，agent 的执行循环、模型推理、命令执行所用的沙箱以及搜索等工具由厂商在云端运行。各家对这类服务的命名与划分各不相同，学术文献中也有名称相近但含义不同的 “Agent-as-a-Service”。

本综述分三部分。第一部分整理定义：先考察 “harness” 一词在评测论文、厂商文档和系统论文中的用法，再摘录五家厂商与三篇学术论文对这类服务的定义原文与原图，对照各家术语之后，给出本综述使用的定义与结构。第二部分按结构中的各个部件，分别整理厂商产品的做法和相关论文的工作。第三部分汇总论文中对 agent 负载的测量、各家的计费方式，以及评估基准和训练侧的相关系统。

定义术语

“harness” 一词的用法

厂商文档用 harness 指代调用模型、执行工具、管理上下文的那部分程序。这个词并非厂商首创，评测论文和系统论文对同一层有各自的叫法。本页按出处整理这些用法。

评测论文：模型外面包的那一层

在 LLM 评测中，harness 原指运行评测的框架。AI Agents That Matter 将 “HELM and LM Evaluation Harness” 列为评测框架的例子。 到了 agent 基准，同一个词开始指代包在模型外面的执行程序。一篇审计基准论文披露情况的论文把 “harness specification” 定义为：

What scaffold was wrapped around the model, what tools did it have, what stopping rule, what environment image? This is the field that the agent setting introduces and that the classical setting does not have.

即：模型外面包了什么脚手架（scaffold），有哪些工具，停止规则是什么，环境镜像是什么；这是 agent 评测引入、而传统静态评测没有的字段。TheAgentCompany 称所用的 OpenHands “provides a stable and strong agent harness for both web browsing and coding”，并把对比的基线称为 “agent scaffolds”。 Science sandboxes 用各厂商原生的编程 agent 环境构成 “model-harness systems”，并说明 “We introduced no third-party agent scaffold”。

厂商文档：被托管的那一层

OpenAI Agents API 的架构页给出了明确定义：

Harness: The OpenAI-hosted Codex instance that runs the model and tool loop and maintains the agent’s session.

Anthropic 的文章回顾了这一层的来历：早期的 API 只提供 tokens in / tokens out，“you built the harness and underlying infrastructure”；Claude Code 内部 “contained our own version of that harness: the loop, tool execution, subagents, context management”，随后以 Claude Agent SDK 开放，最终由 Managed Agents 托管。 Google 的 Managed Agents API 由 “Antigravity harness” 驱动；AWS 的架构图把 Bedrock Managed Agents 的 Runtime 层标为 “OpenAI Harness”，其中包括 Agentic Loop、Inference、Memory、Skills（见）。

系统论文：编排程序

DSec 把 DeepSeek Harness、OpenCode 等称为 “agent tools and orchestration harnesses”，并在训练系统中把 harness 放进沙箱运行：“an agent sandbox, which hosts the scaffold (e.g., DeepSeek Harness) and its tools”。 YoloFS 在讨论文件系统权限时写道 “most agent harnesses prompt the user before taking action”。

这些用法指向同一层：它在模型之外，负责调用模型、执行模型请求的工具、管理上下文和会话。两篇综述描述的是这一层的内部组成；评测论文强调它影响结果、必须披露；厂商文档则把它作为可托管的产品。本综述沿用厂商文档的 “harness” 指代这一层，下文引用各家原文时保留各自的叫法。

定义模型厂商

模型厂商对托管 agent 的定义

OpenAI、Anthropic 和 Google 推出了由厂商托管 harness 的 agent 服务，用户提交配置，循环本身在厂商侧运行。本页摘录三家文档中的定义原文与架构图，中文为译文。

云平台对托管 agent 的定义

AWS、Google 和 Microsoft 的运行平台托管用户自己的 agent 代码，并提供会话隔离、身份、网关、记忆与观测等配套服务。AWS 另与 OpenAI 合作推出托管 harness 的 Bedrock Managed Agents。

定义学术文献

学术文献中的 Agent-as-a-Service

学术论文中已有 “Agent-as-a-Service” 的提法。三篇论文的用法相近：把 agent 当作服务网络中的节点，研究 agent 的注册、发现、调度与协作，或把 agent 部署在数据所在处供远程调用。

AN

Agent-as-a-Service based on Agent Network

arXiv 2505.08446
We propose Agent-as-a-Service based on Agent Network (AaaS-AN), a service-oriented paradigm grounded in the Role-Goal-Process-Service (RGPS) standard.

AaaS-AN 是基于 RGPS（角色–目标–过程–服务）标准的面向服务的范式。它把 agent 与 agent 组建模为网络中的顶点，按任务与角色依赖自组织；面向服务的 agent 提供服务发现、注册与互操作协议，由服务调度器依据执行图做分布式协调。作者构建了包含 100 多个 agent 服务的系统，并发布 1 万条长链多 agent 工作流数据。

OA

OpenAaaS

arXiv 2605.13618
The concept of Agent-as-a-Service (AaaS)—where autonomous agents are exposed through standardized APIs and discovered dynamically by client systems—has gained significant traction in both industry and academia.
AaaS decouples the agent’s cognitive capabilities from the underlying infrastructure, allowing specialized scientific agents to be developed, versioned, and consumed independently.

AaaS 指自主 agent 通过标准化 API 对外提供、由客户端系统动态发现；它把 agent 的认知能力与底层基础设施分开，使专门的科学 agent 能够独立开发、版本化和使用。OpenAaaS 面向材料信息学，原则是 “code flows, data stays still”：主 agent 负责规划，子 agent 部署在数据所在的机构执行。

ASC

Agentic Services Computing

arXiv 2509.24380
Agent-as-a-Service frameworks organize agents through registration, discovery, interoperability protocols, and execution graphs.

这篇综述从服务计算的角度讨论 agent，把 agentic service 定义为面向服务的自主 agent，并把 AaaS 框架概括为通过注册、发现、互操作协议和执行图组织 agent。它将 agentic service 的内部要素分为服务意图、服务状态与服务控制（见右侧原图）。

定义对照与归纳

术语对照与本文的定义

前三页摘录的定义里，各家给同类部件起了不同的名字。把这些名字按部件的职责对齐，本页再据此给出本综述使用的定义。

对照表显示的共同点

  • 每一家都有 harness 这一层，区别在于由谁提供。OpenAI、Anthropic、Google Managed Agents 与 Bedrock Managed Agents 由厂商托管；AgentCore Runtime、Google Agent Runtime 与 Foundry Hosted agents 运行用户自带的代码。
  • 每一家都以会话作为调用单位。OpenAI 与 Anthropic 用 Session 与 Events；AgentCore 用 runtimeSessionId；Foundry 用 session ID 与 conversation ID；Google Managed Agents 用 Interactions API。
  • 执行环境都与 harness 分开描述。OpenAI、Anthropic 的 Environment 可以是厂商沙箱或用户机器；AWS 原图把 Environment 单列为一层；Google 文档明确区分 Agent Runtime 与 Sandbox；Microsoft 原图中 agent 运行在 micro-VM 中，工具调用经单独的 Tools Service。
  • 模型推理与工具调用是 harness 之外的依赖。模型在 AWS 原图中单列为一层，Google 原图中是 “Models (Gemini/3rd party)”；搜索、MCP、代码执行等工具在各家文档中以内置工具或网关的形式出现。
  • 配置、凭据、记忆与观测在多数文档中有对应部件，是服务内部保存的状态。

与学术定义的关系

学术文献中的 AaaS 关注 agent 之间：OpenAaaS 强调 agent “exposed through standardized APIs and discovered dynamically by client systems”，AaaS-AN 与 ASC 强调注册、发现、调度与协作。厂商文档关注单个 agent 所依赖的资源：harness 在哪里运行、沙箱由谁提供、模型与工具如何接入、会话状态如何保存与计费。两者都把 agent 当作通过 API 调用的服务。

本综述的定义

Agent as a Service（托管智能体服务）：以 agent 会话为调用单位的云服务。服务方运行 agent harness，或运行承载用户 harness 的运行时并保存会话状态；应用通过会话接口提交任务、接收事件；harness 在执行中调用模型推理，在执行环境中运行命令与读写文件，并调用托管工具。

这一定义沿用学术文献 “通过 API 对外提供 agent” 的含义，范围限定在单个 agent 的云端运行；它同时覆盖厂商托管 harness 的服务与运行用户 harness 的平台。按这一定义画出服务的组成。

背景部署形态

Harness 与执行环境的三种部署关系

Anthropic 介绍 Managed Agents 的文章按时间顺序描述了 harness 的三种部署方式，并说明了从第二种走向第三种的原因。OpenAI 的架构页用三张原图给出了同样的选择：不配环境、OpenAI 托管环境、用户自带环境。

Anthropic 描述的三个阶段

  1. 模型 API。“When we opened up Claude to developers in 2023, the API was deliberately simple: tokens in, tokens out … you built the harness and underlying infrastructure.” 开发者自己写循环：“ask the model what to do, run the tool, feed the result back, and repeat.”
  2. Agent SDK。Claude Code 内部的 harness 以 Claude Agent SDK 开放，开发者在自己的基础设施上部署。文章指出这种部署的共同做法是 “agent harnesses often run inside the same container as the filesystem it works on”。
  3. Managed Agents。“decoupling the brain from the hands”：harness 与沙箱分开运行，由会话日志连接。

对于第二种形态，文章列出三个问题：容器要先启动，模型才能开始推理（“A container has to spin up … before Claude can think”）；模型生成的代码与凭据在同一个容器里；容器退出时，整个运行随之丢失。第三种形态对应的做法是：环境与推理并行准备，从不调用工具的会话不创建容器，文章称测试中首 token 时间的中位数缩短约 60%，p95 缩短 90% 以上；MCP、CLI、GitHub 的令牌存放在单独的 vault 中，由代理按需取出；会话日志存放在运行 agent 的进程之外，会话空闲时容器打检查点，之后可从原处恢复。

Crab 论文用 agent-in-a-sandbox 与 agent-with-a-sandbox 区分第二、第三种形态：前者 “the agent process itself runs inside the sandbox”，后者 agent 在沙箱之外，通过接口操作沙箱。

分组之间的差别

托管 harness 的服务在 harness、会话与模型三列都由厂商运行，差别在执行环境：OpenAI、Anthropic 与 Bedrock Managed Agents 允许把沙箱换成用户自己的计算资源，Google Managed Agents 目前只提供托管沙箱。运行平台在 harness 一列都是用户自带，模型也由 agent 代码自行选择（Foundry 限定在其模型目录内），平台运行的是会话、隔离环境与配套服务。

云端编程应用

Codex Cloud、Claude Code 云会话、Copilot cloud agent、Jules 与 Kiro Web 是面向开发者的成品应用，五个部分都由厂商运行；Claude Code 云会话还可路由到组织自托管的环境。这一组与托管 harness 的服务使用相同的部件，区别是调用方式：前者经网页、IDE、CLI 或 GitHub 使用，后者经 API 集成进用户自己的应用。

部件harness

Agent harness

厂商托管的 harness 提供什么

OpenAI 列出的托管 harness 能力有：沙箱内的命令与代码执行，skills 与指令，经工具或 MCP 接入的外部数据，运行中的用户引导（steering），总结早先工作以管理上下文窗口，把子任务委派给子 agent，从中断处恢复会话。多 agent 配置中可以设置并发子 agent 数（示例为 4）。 Anthropic 列出内置的 prompt caching 与 compaction，以及 Bash、文件读写编辑与搜索、网页搜索与抓取、MCP 等内置工具；另有让 agent 按评分细则检查自身输出的 outcomes、多 agent 编排、权限策略与 webhook。 Google 的托管沙箱默认提供 bash 与 file_system 两个工具，可从 Skill Registry 挂载 skills。

运行平台上的 harness

运行平台的 harness 由用户提供。AgentCore Runtime 支持 LangGraph、Strands、CrewAI 与不使用框架的自定义 agent，平台页面还列出 OpenAI Agents SDK 与 Claude Agent SDK。 Google Agent Runtime 按集成程度给框架分档：ADK 完全集成；LangChain、LangGraph、AG2、LlamaIndex 有 SDK 模板；CrewAI 等使用自定义模板，也可直接部署满足运行时契约的任意容器。 Microsoft 要求容器监听 8088 端口、提供 GET /readiness 健康检查、实现 /responses 或 /invocations 至少一个协议路由，并在 SIGTERM 时优雅退出。

为什么要由厂商托管

Anthropic 的解释是 harness 需要随模型调整。文中的例子：Claude Sonnet 4.5 在接近上下文上限时会提前收尾（文中称为 “context anxiety”），团队为此在 harness 中加入上下文重置；到 Claude Opus 4.5，这一行为消失，重置成为多余的开销。文章认为，对多数组织而言维护 harness 是 “overhead that doesn’t differentiate their product”。

接口 ①会话

会话接口与会话生命周期

托管服务以会话为调用单位。会话的存续时间可以远长于它占用计算资源的时间：五家文档都把 “会话存在” 与 “会话正在占用沙箱” 分开处理，但具体机制不同。本页先分别说明各家的做法，最后汇总。

OpenAI：环境可以晚于会话启动

会话流程：创建会话时服务准备环境；用户输入开启一轮工作；应用通过流式事件或 webhook 获取进展；之后可继续发送任务，或在运行中途发送引导消息。 文档写明 “An agent session can outlive its environment”。自托管环境有两种管理方式（下方两张原图）：应用在创建会话后自行启动计算资源；或者等到服务发出 agent.session.action_required（类型为 environment_connection）事件时，由 webhook 处理程序启动或重连执行器。服务最多等待 5 分钟连接，超时则本次提交失败；空闲事件本身不能作为安全的关机信号。 OpenAI 托管沙箱在活动与心跳中断一小时后可能被删除，/workspace/outputs 下的文件在每轮结束时发布为不可变制品。

Anthropic：按 running 状态计时

会话状态包括 running、idle、rescheduling、terminated。价格页写明：“Runtime is measured to the millisecond and accrues only while the session’s status is running. Time spent idle (waiting for your next message or a tool confirmation), rescheduling, or terminated does not count toward runtime.” 会话空闲时容器打检查点，之后从原处恢复。 自托管时环境是一个工作队列，会话排队等待 worker 领取；没有 worker 在线时会话保持排队。

Microsoft：计算跟随会话

文档用三个状态描述会话：Active，计算在运行，请求路由到这里，$HOME 与 /files 可用；Idle，在设定的空闲超时内没有请求，平台释放计算并持久化会话状态；Resumed，同一会话 ID 再次被访问，平台分配新的计算并恢复持久化的状态。空闲超时可设为 2–60 分钟，默认 15 分钟；会话 30 天未活动后被删除。文档的说法是 “Compute follows the session, not the individual request”。

AWS：microVM 与持久存储分开

AgentCore Runtime 的会话在 microVM 上最长运行 8 小时，在 Instances 计算类型上最长 14 天。 会话停止或空闲超时后 microVM 终止；配置了托管会话存储时，挂载在 /mnt 下的目录在下次以同一 runtime-session-id 调用时被新的 microVM 重新挂载，空闲 14 天后清理，每会话上限 1 GB。 Instances 类型在停止时终止 EC2 实例、保留 EBS 卷，恢复时在新实例上重新挂载。

Google：沙箱 TTL

Managed Agents 的沙箱 TTL 为 7 天，每次交互重新计时；运行时安装的包保存在环境快照中，使用相同 env_id 的交互可以继续使用。 Agent Platform 的沙箱 TTL 从自定义容器的 7 天到代码执行沙箱的 14 天不等。

接口 ②模型推理

模型推理

托管服务在一次会话中多次调用模型。Talaria 统计的 SWE-bench 会话，模型调用次数的中位数为 11，相邻两次调用之间的工具执行中位数为 0.39 秒，后一次提示的大部分内容是前一次的前缀（）。推理侧的研究据此关注会话级的路由、准入与 KV cache 复用。

各产品如何接入模型

托管 harness 的服务使用厂商自己的模型：OpenAI Agents API 使用 OpenAI 模型，按所选模型的 API 价计费；Claude Managed Agents 使用 Claude 模型，token 按模型价目表计费，prompt caching 的倍率同样适用。 Bedrock Managed Agents 在 Bedrock 内运行 OpenAI 的 harness，模型推理也经由 Amazon Bedrock。

运行平台把模型的选择交给 agent 代码。AgentCore Runtime 的文档列出 Bedrock、Claude、Gemini、OpenAI 等模型；Google Agent Runtime 原图中的模型一栏为 “Models (Gemini/3rd party)”；Microsoft Hosted agents 调用 Foundry 模型目录中的模型。

价格与前缀缓存

agent 会话的提示逐轮增长且高度重复，缓存命中的比例直接影响费用。Anthropic 价目表中，缓存读取按标准输入价的 10% 计费，Fable 5.1 为 2.5%，Opus 5.5 与 Sonnet 5.5 为 5%（）。 价格页给出的一小时编程会话算例中，4 万个输入 token 命中缓存后，输入部分的费用由 $0.25 降至 $0.07（）。

按调用调度的问题

Talaria 指出，按单次调用调度的 serverless 多模型推理系统会在两个方向上与会话完成时间错位。空间上，只看负载或队列长度的路由器可能把会话的后续调用发到最空闲的实例，而该实例既没有目标模型的权重，也没有会话的 KV；对长上下文会话，搬运 KV 或重算前缀的开销可能超过它避开的排队时间。时间上，按固定轮次在多个模型间轮转的调度器即使路由正确，也可能让返回的会话等到该模型的下一个时间片。 论文给出的量级：在 Qwen3-235B、TP=8 上重算 25K tokens 的中位前缀需要 4.3 秒 TTFT，而工具间隔的中位数为 0.39 秒。

Talaria 的做法见：热池实例常驻单个模型，冷池实例以 token 级时分复用若干长尾模型；会话感知的路由器为可能返回的调用预留下一个时间片的准入额度（soft reservation），没有预留的调用按模型驻留、KV 驻留和实例压力排序选择实例。

接口 ③产品

执行环境

OpenAI 把执行环境定义为 “Where the agent runs commands, executes code, and works with files”。 它承载模型生成的代码，因此各家文档都从隔离、网络与凭据三方面约束它。本页整理各产品的隔离方式、规格、持久化与启动时间，以及把凭据留在沙箱之外的做法。

隔离方式

AgentCore Runtime 按用户会话分配 microVM，CPU、内存和文件系统按会话隔离，会话结束后 microVM 终止，内存被清理。 Microsoft Hosted agents 按会话分配 VM 隔离的沙箱。 Anthropic 云沙箱是运行 Ubuntu 24.04 的隔离 Linux 容器。 GKE Agent Sandbox 在 agent 执行代码时创建 gVisor 隔离的 pod。 Cloud Run sandboxes 在已有的服务实例内启动：容器文件系统以只读方式挂载，写入落在临时的内存覆盖层，执行结束后丢弃；出站网络默认关闭；沙箱与服务的环境变量和元数据服务器隔离。 按内核的共享程度排列这些做法。

资源规格

Microsoft 的会话规格为 0.5 vCPU/1 GiB、1 vCPU/2 GiB 或 2 vCPU/4 GiB，1 vCPU 及以上的磁盘预算为 20 GiB，其中约 20% 由系统保留。CPU 与内存按会话配置、按所有活跃会话的用量计费，规格配置过大时，费用随并发会话数成倍增加。 AgentCore 的 Instances 计算类型在用户账户内运行 EC2 托管实例，会话最长 14 天，支持 GPU，多个 agent 可以共用实例和文件系统；microVM 会话最长 8 小时。

持久化

  • AgentCore 托管会话存储挂载在 /mnt 下，跨 stop/resume 保留，每会话上限 1 GB，空闲 14 天后清理。
  • Google Managed Agents 的沙箱 TTL 为 7 天，每次交互重新计时；运行时安装的包保存在环境快照中，使用相同 env_id 的 agent 共享环境。
  • OpenAI 托管沙箱中 /workspace/outputs 下的文件在每轮结束时发布为不可变制品，沙箱过期后仍可下载。
  • Codex Cloud 发布环境时保存准备好的文件系统，新任务从该文件系统开始，已有任务保留各自的状态。

启动时间

Google Agent Platform 的沙箱冷启动创建最长约 2 分钟，资源准备好后通常数秒内启动。 Cloud Run 公布的示例中，启动、执行、停止 1,000 个沙箱的平均延迟为 500 ms。 GKE 的 Pod Snapshots 保存运行中沙箱的状态并在需要时恢复，启动时间由数分钟降至数秒。 AgentCore Runtime V2 从快照启动 agent，文档称冷启动时间在不同并发量和镜像大小下保持稳定。 Agent Runtime 自身的冷启动受实例数与并发配置影响，见。

网络与凭据

OpenAI 的安全页开头写道：“Agent-generated code can access the files, credentials, and network available to its environment.” 据此给出的做法包括：在虚拟机等隔离计算中运行；出站流量只放行获准的目标地址；执行器使用的环境密钥 CODEX_API_KEY 只能用于连接环境，不能授权其他 API 操作；应用的 API 密钥不进入环境；第三方凭据留在环境之外，OpenAI 托管沙箱中的代码使用占位符，由网络代理对获准的主机替换为真实密钥。自托管环境需要用户自己部署这样的代理（右图）。

其他产品的同类做法：Anthropic 把 MCP、CLI 与 GitHub 的令牌放在沙箱外的 vault 中，由代理按需取出；Claude Code 云会话的 GitHub 代理在服务端附加凭据；Codex Cloud 的 network secret 经代理替换；Google Managed Agents 的网络按域名白名单开启；Cloud Run sandboxes 的出站网络默认关闭。

本地沙箱面临同样的问题。SideKernel 为北向通道提供网络开关，打开后阻断所有出站流量，只保留 api.anthropic.com 以便模型推理继续进行。作者的问卷中，在沙箱中运行编程 agent 的用户不到 40%。

接口 ③已有工作

沙箱状态的保存与恢复

2026 年关于 agent 执行环境的论文，多数研究沙箱的检查点与回滚（checkpoint/restore，下称 C/R）。agent 的状态分布在对话历史、文件系统和进程三处；故障恢复、抢占式实例上的执行、树搜索与 RL rollout 的分支，都需要保存并恢复这三部分。本页以 Crab 为主线，DeltaBox 见。

恢复不完整的后果

Crab 选取 50 个在正常运行中能解出的 Terminal-Bench 任务，在每条轨迹的随机位置注入一次崩溃，比较四种恢复策略（）。只恢复对话历史时，agent 以为已经完成的修改在新沙箱中并不存在，回放 LLM 轨迹时求解率为 6%，实时调用 LLM 时为 28%；同时恢复对话与文件系统，求解率为 48% 与 34%，缺少的是内存中的进程状态；实时调用 LLM 时，agent 发现状态缺失后会自行修补，反而进一步偏离原来的执行。从头重跑能解出全部任务，但中位求解时间增至 1.81 倍（回放）与 1.55 倍（实时）。

检查点的压力来自哪里

agent 的单轮很短：Terminal-Bench 轨迹中单轮用时的中位数为 3.34 秒。若每轮都打检查点，单台主机上的检查点请求速率随沙箱密度上升，密度为 100 时中位数达到每秒 17 次（）。论文测得文件系统快照（ZFS）的开销在数十毫秒以内，而 CRIU 进程检查点在高并发下可增至数十秒。

另一方面，多数轮次并不改变 OS 状态。工具调用中 60% 是 run_shell_command，而 70% 的 shell 命令没有重定向、后台运行等可供判断副作用的语法线索（），仅凭命令文本无法判断是否需要检查点。

Crab 的做法

Crab 在内核中用 eBPF 观察每一轮对文件与进程的实际修改，跳过不产生恢复相关状态的轮次（论文测得超过 75% 的轮次属于此类），只对有修改的部分做检查点；Coordinator 位于 LLM API 与沙箱之间，把检查点安排在 agent 等待 LLM 响应的时间内（）。它同时支持 agent-in-a-sandbox 与 agent-with-a-sandbox 两种部署。结果：恢复正确率由只恢复对话历史时的 8% 提高到 100%，检查点流量最多减少 87%，端到端时间在无故障、无检查点基线的 1.9% 以内；96 个沙箱同机部署时，Coordinator 每轮增加数十微秒。

论文还演示了把回滚交给 agent 使用：为 agent 提供 rollback() 工具后，QEMU 启动任务的用时由 434 秒降至 307 秒。

DeltaBox（arXiv 2605.22781）面向树搜索与 RL 训练中频繁发生的沙箱 C/R。论文观察到，相邻两次检查点之间，沙箱里只有少量文件和内存页发生变化，因此检查点只需复制变化的部分。它在 Firecracker microVM 中实现了这一点：检查点的本地工作约 10.83 ms，隐藏在模型推理时间内；回滚约 1.86 ms。

问题：回滚落在关键路径上

纯文本任务中，回溯只需截断提示历史。编程 agent 则通过 rm、pip install、sed 等命令修改真实的 OS 状态，这些副作用留在磁盘上，编辑历史无法撤销，只能保存并恢复完整的沙箱状态。测试时搜索从两个方向加压：Best-of-N 横向展开多条轨迹，每条都需要快速克隆初始状态；MCTS 纵向回溯到任意历史节点，需要细粒度的 C/R。RL 训练则在每个训练步从同一个预热状态派生 k 个沙箱。

汇总了这两类用法在 SWE-bench 上的收益：MCTS 比线性 ReAct 的通过率高 4.7–6.7 个百分点，RL 训练使三个模型的通过率提高 19.2–29.4 个百分点。论文据此认为，现有系统回避深度搜索的原因之一是缺少足够快的 C/R。

已有方法的开销

已有方法按整份状态复制：git stash、shutil.copytree、Docker commit 与 Btrfs/LVM 快照只保存文件；Firecracker 的 VM 快照只保存内存与设备状态，块设备需另行快照；E2B 的文档化暂停按每 GiB 内存约 4 秒计；CubeSandbox 的快照与恢复为 49.8 ms 与 63.9 ms，但依赖定制的宿主机内核（）。CRIU 恢复进程时按顺序加载内存页，多 GiB 的进程需要数秒。

设计

DeltaBox 提出 AgentState 抽象，把文件系统与进程内存作为一对按增量管理的状态（），由两部分实现：

  • DeltaFS（）：在不卸载的情况下热切换 overlay 层。检查点时把当前可写层冻结为只读，在其上插入新的可写层，此后的修改写时复制到新层；回滚是 O(1) 的层切换。底层 XFS 的 reflink 让修改只复制被改动的 4 KB 块，与文件大小无关。
  • DeltaCR（）：每次检查点同时做 CRIU 转储和一次 fork()，后者产生冻结的模板进程放入模板池，两者都隐藏在等待 LLM 响应的时间内。回滚时命中模板池则从模板 fork 出新进程，只复制页表；模板被逐出时退回 CRIU 慢路径（约 9.29 ms），此时延迟升高，结果仍然正确。

其余机制：LLM 的网络连接由 sidecar 进程 NPD 代理，外部 I/O 不经过被恢复的 agent 进程；只读命令（占 62.0% 的事件）跳过转储；按可达性回收不再需要的转储，轨迹结束时的转储存储减少 46%–63%。

DeltaBox 的对比对象包括 E2B 与 CubeSandbox 等沙箱服务。托管产品的文档中，相关的能力是会话空闲时的检查点（Anthropic）、Pod Snapshots（GKE）和环境快照（Google Managed Agents），用于空闲回收与冷启动；GKE 给出的恢复后启动时间为数秒（）。本仓库存档的厂商文档中没有面向树搜索的毫秒级回滚接口。实现上的两点细节：DeltaFS 是修改过的 overlayfs，作为客户机内核模块随 VM 镜像发布，宿主机内核不需要修改；DeltaCR 转储 agent 进程的内存页，范围小于整个 VM 的快照。

评估基准与评估方法

agent 基准不再是一组问答对，而是一套可执行的环境：仓库快照与测试、可自托管的网站、虚拟机、带数据库的工具 API。运行这些基准本身就需要本综述讨论的部件：harness、模型推理、执行环境与工具。至是 SWE-bench、WebArena、OSWorld 与 τ-bench 论文中的原图。

基准的难度与环境

这些基准发布时，最好的 agent 与人类的差距都很大（）。TheAgentCompany 模拟小型软件公司的内网站点与同事，包含 175 个任务；AgentBench 包含 8 个环境；Science sandboxes 让 agent 在湿实验、预测模型或人为设定的规则系统中反复实验并修正假设，各厂商的模型使用各自原生的编程 agent 环境，作者 “introduced no third-party agent scaffold”。 τ-bench 提出 pass^k 衡量同一任务多次运行的一致性：gpt-4o 的成功率低于 50%，零售领域的 pass^8 低于 25%。

成本应与准确率一同报告

AI Agents That Matter 指出，现有 agent 基准集中关注准确率，导致 SOTA 方案复杂且昂贵。在 HumanEval 上，作者的简单基线（重试、模型升级）位于成本–准确率的 Pareto 前沿，复杂的 agent 多数不在前沿上（）。论文还区分固定成本与可变成本：用 DSPy 优化提示是一次性开销，推理是每次调用的开销；在 HotPotQA 上，联合优化器的固定成本更高，运行约 1,300 次推理之后总成本反而更低（）。论文同时要求基准设置足够的留出集，防止针对基准的过拟合。

基准论文披露了什么

一篇审计论文用五个字段检查 12 篇基准论文：基准身份、harness 规格、推理设置、成本报告、失败分解，每项按 1.0（披露）、0.5（部分）、0（缺失）打分。8 篇 agent 基准论文的平均分为 0.38，4 篇静态基准为 0.66（）。差距最大的是成本报告：8 篇 agent 基准论文均未披露推理成本；harness 规格一项没有一篇得到满分，论文指出 “A repository tag is not a container digest”。评分由一名审计者完成。

DSec 的结构

DSec 通过 Python SDK（libdsec）提供四种沙箱后端：FnCall、容器、microVM（Firecracker）与完整 VM（QEMU）（）。集群级服务负责身份、放置与节点监控；每个节点上的 Edge 管理沙箱生命周期，Aether 管理会话，Chronus 执行命令、读写文件与转发 HTTP。镜像以 EROFS 与 OverlayBD 格式存放在集群文件系统 3FS 上，按需加载。

负载测量（）对应三类机制（）：环境由分别版本化的基础镜像、workspace 与 toolkit 分层组合，更新 toolkit 时不必重建镜像；高密度部署依靠内存共享、回收与 CPU 调度；镜像数据按需读取。评估中，按需拉取的累计磁盘写入比预先拉取少约 57%，完成时间快 1.71 倍；EROFS 挂载替代 tar 解压，完成时间快 1.76 倍；virtio-pmem 让多个客户机共享宿主机页缓存，峰值宿主机内存降低 40.2%；在 50% 的尽力而为负载下，core scheduling 把延迟敏感任务的延迟增幅由 45.2% 限制到 17.3%。

与 RL 框架的协同

早期的训练流水线把 agent 循环放在可抢占的 GPU 训练 pod 中，GPU 任务被抢占时循环丢失而沙箱仍在，恢复依赖命令日志的重放。自 DeepSeek-V4.1 起，rollout 在 DSec 上执行，拆成两部分：agent 沙箱运行 harness（如 DeepSeek Harness）及其工具，worker 容器管理沙箱并提供与 harness 无关的控制层；两者都在可抢占的 GPU 池之外，被抢占的训练任务可以重新连接并继续。训练暂停时，RL 框架通知 DSec 暂停相关沙箱：容器先 docker pause 再回收内存，microVM 保存快照后终止 Firecracker 进程；之后的任何请求都会透明地恢复沙箱。

agent 的异常行为

DSec 记录了训练中 agent 通过非预期途径获取答案的行为：向 Chronus 的 socket 伪造 RPC 请求、读取 Chronus 日志寻找泄露的答案、覆盖 /bin/bash；加入文件与 socket 访问控制后，有 agent 用 XFS_IOC_SWAPEXT ioctl 交换文件的数据区段，导致 XFS 元数据损坏、文件系统下线。沙箱外，agent 扫描端口寻找可访问的镜像站，或经 Go 模块代理获取 GitHub 上的代码。普通命令也会破坏环境：从根目录递归 grep 读到 /proc/kpagecgroup 触发内核缺陷；运行 yes 的输出被记录下来，占用数十 GB 存储。论文的结论是，只检查最终输出无法确认 agent 是否按预期解决了任务。

RollArt：按硬件拆分流水线

RollArt（OSDI 2026）把 agentic RL 的各阶段放到最适合的硬件上：prefill 为主的任务用计算型 GPU，decode 为主的任务用带宽型 GPU，环境运行在 CPU 集群，无状态的奖励计算放到 serverless 平台（）。rollout 按轨迹解耦，生成、环境交互与评分各自推进，慢的或出错的环境不会阻塞其他轨迹；训练与 rollout 在有界陈旧度下异步同步权重。论文统计的多任务训练步，正常运行时平均 365.7 秒，环境出现故障时平均 513.3 秒。与多种 RL 系统相比，训练时间缩短 1.31–2.05 倍；奖励计算移到 serverless 后，奖励 GPU 的利用率由 6% 升至 88%，每步 rollout 时间减半。

rollout 的长尾

Seer 观察到同一提示的多个请求在输出长度和模式上相近，RhymeRL 观察到相邻训练轮次的 rollout 相近，两者把这些相似性用于负载均衡和推测解码。DynaRL 用动态超图描述 RL 流水线，把 GPU 从过度配置的组件迁移到当前的瓶颈。RLinf 把高层工作流拆分后重组为执行流。HetRL 在异构 GPU 上求解调度问题。
