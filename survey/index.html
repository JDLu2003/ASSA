Agent as a Service
托管智能体服务的结构、现状与已有研究

2026 年，以 agent 为调用对象的云服务陆续上线。应用通过 API 提交任务、接收事件流，agent 的执行循环、模型推理、命令执行所用的沙箱以及搜索等工具由服务方在云端运行。

现状

OpenAI Agents API、Claude Managed Agents、Google Managed Agents API 与 Bedrock Managed Agents 托管 agent 的执行循环；AgentCore Runtime、Google Agent Runtime、Foundry Hosted agents 与 DigitalOcean Managed Agents 运行用户自己的 agent，为每个会话分配隔离的执行环境。Meta 的 Muse 与 OpenAI 的 dots 采用同样的结构：Muse 为每个用户分配一台 Muse Secure VM，agent 在其中使用浏览器、邮件与已连接的应用，所有出站请求经 Sentinel 审批；每个 dot 有自己的云端计算机与浏览器，在两次对话之间继续推进任务，用户可以随时打开它的计算机查看或接管。 Codex Cloud、Claude Code 云会话与 Copilot cloud agent 在云端沙箱中执行编程任务。

模型 API 的调用单位是一次请求，这类服务的调用单位是一个 agent 会话。一次会话包含十余次到数十次模型调用与工具执行，可以持续数小时到数天，期间要保存上下文、文件与进程状态，并持有访问外部服务的凭据。 Satya Nadella 介绍 Foundry Hosted agents 时写道 “Every agent will need its own computer”；Cloudflare 推出 @cloudflare/computer 时的说法是 “give every agent a computer of its own”。 DigitalOcean 认为，计量单位由 VM 小时变为 token 与 microVM 秒，云的架构、安全与计费方式都随之改变。 这一变化也反映在硬件上：Tom’s Hardware 测得 Muse 的每台虚拟机使用 2 个 CPU 核与 8 GB 内存，CNBC 报道 Muse 走红推动 AMD 股价创新高，原因是 agent 带动了 CPU 需求。

这类服务的数量增长很快，2026 年 9 月就有 Muse、DigitalOcean Managed Agents 与 dots 相继发布。 各家对服务组成的划分与命名并不一致：OpenAI 把托管的循环称为 harness，AWS 把它画作 Runtime 层，Google 区分 Agent Runtime 与 Sandbox，Microsoft 把平台的职责概括为访问入口、身份、扩缩容与会话状态。学术文献中的 Agent-as-a-Service 指可注册、发现与组合的 agent 网络，所指对象与厂商的托管运行时不同。度量方面，agent 基准评测的是模型与 harness 组合的任务成功率，一项对 12 篇基准论文的审计显示，8 篇 agent 基准论文均未报告推理成本； 会话启动延迟、状态保存与恢复的开销、资源利用率等服务层指标散见于各篇系统论文，基于不同的负载与平台测得。

结论
  1. 调度与计费需要以 agent 会话为单位。会话持续数分钟到数天，大部分时间在等待模型响应，CPU 使用稀疏，内存与文件状态持续占用（）。按单次请求调度推理、按存续时间计费沙箱，都与会话的实际资源使用错位（、）。
  2. 服务的边界需要一套共同的结构来描述。harness 由谁运行、执行环境由谁提供、凭据与会话状态保存在哪里，决定了隔离、恢复与计费的责任归属。各家命名不同，比较产品之前需要先对齐部件（、）。
  3. 服务层的性能与成本缺少度量方法。任务基准衡量成功率，系统论文各自测量自己的负载，厂商的计费口径分为会话运行时长、活跃 CPU 时间与沙箱存续时间；启动延迟、状态恢复开销与单任务成本尚无共同的测量口径（）。

本文据此给出托管智能体服务的定义与结构，按结构中的部件对照各家产品，并整理相关研究、负载测量、计费方式与评估方法。

概念

Harness 的含义

评测论文、厂商文档和系统论文都使用 harness 一词，所指的范围各不相同。在 LLM 评测中，它指运行评测的框架；在 agent 基准中，它指包在模型外面、影响评测结果的执行程序；在厂商文档中，它指可以托管的 agent 循环；在系统论文中，它指放进沙箱运行的编排程序。

评测论文

AI Agents That Matter 把 “HELM and LM Evaluation Harness” 列为 LLM 评测框架的例子。 在 agent 基准中，模型外面的程序成为评测对象的一部分。一篇审计基准论文披露情况的论文把 “harness specification” 定义为：

What scaffold was wrapped around the model, what tools did it have, what stopping rule, what environment image? This is the field that the agent setting introduces and that the classical setting does not have.

即模型外面的脚手架（scaffold）、可用的工具、停止规则与环境镜像，这一字段随 agent 评测出现。TheAgentCompany 称其使用的 OpenHands “provides a stable and strong agent harness for both web browsing and coding”，并把对比的基线称为 “agent scaffolds”。 Science sandboxes 把各厂商的模型与其原生编程 agent 环境合称 “model-harness systems”。

厂商文档

OpenAI Agents API 的架构页写道：

Harness: The OpenAI-hosted Codex instance that runs the model and tool loop and maintains the agent’s session.

Anthropic 的文章回顾了这一层的来历：早期的 API 是 tokens in / tokens out，“you built the harness and underlying infrastructure”；Claude Code 内部 “contained our own version of that harness: the loop, tool execution, subagents, context management”，后来以 Claude Agent SDK 开放，再由 Managed Agents 托管。 Google 的 Managed Agents API 由 “Antigravity harness” 驱动；AWS 的架构图把 Bedrock Managed Agents 的 Runtime 层标为 “OpenAI Harness”，包括 Agentic Loop、Inference、Memory、Skills（）。

系统论文

DSec 把 DeepSeek Harness、OpenCode 等称为 “agent tools and orchestration harnesses”，训练时把它们放进沙箱：“an agent sandbox, which hosts the scaffold (e.g., DeepSeek Harness) and its tools”。 YoloFS 讨论文件系统权限时写道 “most agent harnesses prompt the user before taking action”。

综述中的 agent 结构

两篇综述描述了这一层程序的内部组成：Wang 等人把 LLM 自主 agent 分为 profile、memory、planning、action 模块；Xi 等人分为 brain、perception、action，并把 agent 放在与环境交互的循环中（右侧两图）。

本文中的 harness 沿用厂商文档的用法，指模型之外的程序，负责模型调用、工具执行、上下文与会话管理。

与 Agent-as-a-Service 论文的关系

三篇 Agent-as-a-Service 论文研究 agent 之间的关系：OpenAaaS 强调 agent “exposed through standardized APIs and discovered dynamically by client systems”，AaaS-AN 与 Agentic Services Computing 研究注册、发现、调度与协作。厂商文档描述单个 agent 运行所需的资源：harness 的运行位置、沙箱的提供方、模型与工具的接入、会话状态的保存与计费。两类文献都把 agent 当作通过 API 调用的服务。

本文的定义

Agent as a Service（托管智能体服务）：以 agent 会话为调用单位的云服务。服务方运行 agent harness，或运行承载用户 harness 的运行时并保存会话状态；应用通过会话接口提交任务、接收事件；harness 在执行中调用模型推理，在执行环境中运行命令与读写文件，并调用托管工具。

定义沿用 Agent-as-a-Service 论文 “通过 API 对外提供 agent” 的含义，范围是单个 agent 的云端运行，覆盖厂商托管 harness 的服务与运行用户 harness 的平台。是按此定义画出的服务结构。

Harness 与执行环境的部署关系

Anthropic 介绍 Managed Agents 的文章按时间顺序描述了 harness 的三种部署方式，并说明了第三种方式的由来。OpenAI 的架构页给出了对应的三种环境配置：无环境（none）、OpenAI 托管环境、用户自带环境。

Anthropic 描述的三个阶段

  1. 模型 API。“When we opened up Claude to developers in 2023, the API was deliberately simple: tokens in, tokens out … you built the harness and underlying infrastructure.” 循环由开发者编写：“ask the model what to do, run the tool, feed the result back, and repeat.”
  2. Agent SDK。Claude Code 内部的 harness 以 Claude Agent SDK 开放，开发者在自己的基础设施上部署。文章写道，这种部署通常把 harness 与它操作的文件系统放在同一容器中（“agent harnesses often run inside the same container as the filesystem it works on”）。
  3. Managed Agents。harness 与沙箱分开运行，由会话日志连接，文章称之为 “decoupling the brain from the hands”。

文章列出第二种方式的三个问题：容器启动之后模型才能开始推理（“A container has to spin up … before Claude can think”）；模型生成的代码与凭据处在同一容器；容器退出时整个运行随之丢失。第三种方式的对应做法是：环境与推理并行准备，容器在首次执行工具时才创建，测试中首 token 时间的中位数缩短约 60%，p95 缩短 90% 以上；MCP、CLI、GitHub 的令牌存放在 vault 中，由代理按需取出；会话日志存放在运行 agent 的进程之外，会话空闲时容器打检查点，之后从原处恢复。

Crab 论文把第二、第三种方式称为 agent-in-a-sandbox 与 agent-with-a-sandbox：前者 “the agent process itself runs inside the sandbox”，后者的 agent 在沙箱之外，通过接口操作沙箱。

现状

各产品的托管范围

按的结构，逐个产品标出 harness 与各接口由谁运行。产品分为五组：托管 harness 的服务、运行平台、沙箱服务、搜索 API 与云端 agent 应用。

托管 harness 的服务与运行平台

托管 harness 的服务在 harness、会话与模型三列都由厂商运行，差别在执行环境：OpenAI、Anthropic 与 Bedrock Managed Agents 允许把沙箱换成用户自己的计算资源，Google Managed Agents 使用托管沙箱。运行平台在 harness 一列都是用户自带，模型由 agent 代码选择（Foundry 限定在其模型目录内），平台运行会话、隔离环境与配套服务。

云端 agent 应用

Codex Cloud、Claude Code 云会话、Copilot cloud agent、Jules 与 Kiro Web 在云端沙箱中执行编程任务；Muse 与 dots 为每个用户的 agent 分配一台云端计算机，处理邮件、预订、购物与持续进行的工作。 这一组的五个部分都由厂商运行，Claude Code 云会话可以路由到组织自托管的环境，dots 可以连接用户自己的电脑。它们与托管 harness 的服务使用相同的部件，调用方式不同：前者经网页、手机应用、IDE、CLI、GitHub 或聊天软件使用，后者经 API 集成进用户自己的应用。

部件

Harness

厂商托管的 harness

OpenAI 列出的托管 harness 能力有：沙箱内的命令与代码执行，skills 与指令，经工具或 MCP 接入的外部数据，运行中的用户引导（steering），总结早先工作以管理上下文窗口，把子任务委派给子 agent，从中断处恢复会话。多 agent 配置可以设置并发子 agent 数，示例为 4。 Anthropic 列出内置的 prompt caching 与 compaction，Bash、文件读写编辑与搜索、网页搜索与抓取、MCP 等内置工具，以及让 agent 按评分细则检查自身输出的 outcomes、多 agent 编排、权限策略与 webhook。 Google 的托管沙箱默认提供 bash 与 file_system 两个工具，可以从 Skill Registry 挂载 skills。

运行平台上的 harness

AgentCore Runtime 支持 LangGraph、Strands、CrewAI 与自定义 agent，平台页面还列出 OpenAI Agents SDK 与 Claude Agent SDK。 Google Agent Runtime 按集成程度给框架分档：ADK 完全集成；LangChain、LangGraph、AG2、LlamaIndex 有 SDK 模板；CrewAI 等使用自定义模板，满足运行时契约的容器也可以直接部署。 Microsoft 的运行时契约要求容器监听 8088 端口、提供 GET /readiness 健康检查、实现 /responses 或 /invocations 协议中的至少一个，并在收到 SIGTERM 时优雅退出。

托管 harness 的理由

Anthropic 的解释是 harness 需要随模型调整。文中的例子：Claude Sonnet 4.5 在接近上下文上限时会提前收尾，文章称为 “context anxiety”，团队为此在 harness 中加入上下文重置；到 Claude Opus 4.5，这一行为消失，重置成为多余的开销。文章认为，对多数组织而言，维护 harness 是 “overhead that doesn’t differentiate their product”。

接口 ①

会话与会话的生命周期

托管服务以会话为调用单位。会话的存续时间可以远长于它占用计算资源的时间，五家文档都把会话的存在与会话占用沙箱分开处理，具体机制各不相同。

OpenAI

会话的流程是：创建会话时服务准备环境，用户输入开启一轮工作，应用通过流式事件或 webhook 获取进展，之后可以继续发送任务，或在运行中途发送引导消息。 文档写明 “An agent session can outlive its environment”。自托管环境有两种管理方式（下方两图）：应用在创建会话后自行启动计算资源；或者等服务发出 agent.session.action_required 事件（类型为 environment_connection），再由 webhook 处理程序启动或重连执行器。服务最多等待 5 分钟连接，超时则本次提交失败。 OpenAI 托管沙箱在活动与心跳中断一小时后可能被删除，/workspace/outputs 下的文件在每轮结束时发布为不可变制品。

Anthropic

会话状态有 running、idle、rescheduling、terminated，运行时长按 running 状态计费。价格页写明：“Runtime is measured to the millisecond and accrues only while the session’s status is running. Time spent idle (waiting for your next message or a tool confirmation), rescheduling, or terminated does not count toward runtime.” 会话空闲时容器打检查点，之后从原处恢复。 自托管时，环境是一个工作队列，会话排队等待 worker 领取，worker 上线前会话保持排队。

Microsoft

文档用三个状态描述会话。Active：计算在运行，请求路由到这里，$HOME 与 /files 可用。Idle：在设定的空闲超时内没有请求，平台释放计算并持久化会话状态。Resumed：同一会话 ID 再次被访问，平台分配新的计算并恢复持久化的状态。空闲超时可设为 2–60 分钟，默认 15 分钟；会话 30 天无活动后被删除。文档的概括是 “Compute follows the session, not the individual request”。

AWS

AgentCore Runtime 的会话在 microVM 上最长运行 8 小时，在 Instances 计算类型上最长 14 天。 会话停止或空闲超时后 microVM 终止；配置了托管会话存储时，挂载在 /mnt 下的目录在下次以同一 runtime-session-id 调用时由新的 microVM 重新挂载，空闲 14 天后清理，每会话上限 1 GB。 Instances 类型在停止时终止 EC2 实例、保留 EBS 卷，恢复时在新实例上重新挂载。

Google

Managed Agents 的沙箱 TTL 为 7 天，每次交互重新计时；运行时安装的包保存在环境快照中，使用相同 env_id 的交互可以继续使用。 Agent Platform 的沙箱 TTL 从自定义容器的 7 天到代码执行沙箱的 14 天不等。

模型推理

托管服务在一次会话中多次调用模型。Talaria 统计的 SWE-bench 会话，模型调用次数的中位数为 11，相邻两次调用之间的工具执行中位数为 0.39 秒，后一次提示的大部分内容是前一次的前缀（）。推理侧的研究据此关注会话级的路由、准入与 KV cache 复用。

agent 会话的提示逐轮增长且高度重复，缓存命中的比例直接影响费用。Anthropic 价目表中，缓存读取按标准输入价的 10% 计费，Fable 5.1 为 2.5%，Opus 5.5 与 Sonnet 5.5 为 5%（）。 价格页的一小时编程会话算例中，4 万个输入 token 命中缓存后，输入部分的费用由 $0.25 降至 $0.07（）。

按单次调用调度的错位

Talaria 指出，按单次调用调度的 serverless 多模型推理系统会在两个方向上与会话完成时间错位。空间上，按负载或队列长度路由的路由器可能把会话的后续调用发到最空闲的实例，而该实例既没有目标模型的权重，也没有会话的 KV；对长上下文会话，搬运 KV 或重算前缀的开销可能超过它避开的排队时间。时间上，按固定轮次在多个模型间轮转的调度器即使路由正确，也可能让返回的会话等到该模型的下一个时间片。 论文给出的量级：在 Qwen3-235B、TP=8 上重算 25K tokens 的中位前缀需要 4.3 秒 TTFT，工具间隔的中位数为 0.39 秒。

Talaria 的结构见。热池实例常驻单个模型，冷池实例以 token 级时分复用若干长尾模型；会话感知的路由器为可能返回的调用预留下一个时间片的准入额度（soft reservation），没有预留的调用按模型驻留、KV 驻留和实例压力排序选择实例。

接口 ③

执行环境

OpenAI 把执行环境定义为 “Where the agent runs commands, executes code, and works with files”。 执行环境承载模型生成的代码，各家文档从隔离、网络与凭据三方面约束它。

隔离方式

AgentCore Runtime 按用户会话分配 microVM，CPU、内存和文件系统按会话隔离，会话结束后 microVM 终止，内存被清理。 Microsoft Hosted agents 按会话分配 VM 隔离的沙箱。 Anthropic 云沙箱是运行 Ubuntu 24.04 的隔离 Linux 容器。 GKE Agent Sandbox 在 agent 执行代码时创建 gVisor 隔离的 pod。 Cloud Run sandboxes 在已有的服务实例内启动：容器文件系统以只读方式挂载，写入落在临时的内存覆盖层，执行结束后丢弃；出站网络默认关闭；沙箱与服务的环境变量和元数据服务器相互隔离。 按与宿主机共享内核的程度排列这些产品。

资源规格

Microsoft 的会话规格为 0.5 vCPU/1 GiB、1 vCPU/2 GiB 或 2 vCPU/4 GiB，1 vCPU 及以上的磁盘预算为 20 GiB，其中约 20% 由系统保留。CPU 与内存按会话配置、按所有活跃会话的用量计费，规格配置过大时，费用随并发会话数成倍增加。 AgentCore 的 Instances 计算类型在用户账户内运行 EC2 托管实例，会话最长 14 天，支持 GPU，多个 agent 可以共用实例和文件系统；microVM 会话最长 8 小时。

持久化

  • AgentCore 托管会话存储挂载在 /mnt 下，跨 stop/resume 保留，每会话上限 1 GB，空闲 14 天后清理。
  • Google Managed Agents 的沙箱 TTL 为 7 天，每次交互重新计时；运行时安装的包保存在环境快照中，使用相同 env_id 的 agent 共享环境。
  • OpenAI 托管沙箱中 /workspace/outputs 下的文件在每轮结束时发布为不可变制品，沙箱过期后仍可下载。
  • Codex Cloud 发布环境时保存准备好的文件系统，新任务从该文件系统开始，已有任务保留各自的状态。

启动时间

Google Agent Platform 的沙箱冷启动创建最长约 2 分钟，资源准备好后通常数秒内启动。 Cloud Run 公布的示例中，启动、执行、停止 1,000 个沙箱的平均延迟为 500 ms。 GKE 的 Pod Snapshots 保存运行中沙箱的状态并在需要时恢复，启动时间由数分钟降至数秒。 AgentCore Runtime V2 从快照启动 agent，文档称冷启动时间在不同并发量和镜像大小下保持稳定。 Google Agent Runtime 的冷启动随最小实例数与并发配置变化（）。

网络与凭据

OpenAI 的安全页开头写道：“Agent-generated code can access the files, credentials, and network available to its environment.” 对应的做法有：在虚拟机等隔离计算中运行；出站流量只放行获准的目标地址；执行器使用的环境密钥 CODEX_API_KEY 仅用于连接环境；应用的 API 密钥保存在环境之外；第三方凭据留在环境之外，OpenAI 托管沙箱中的代码使用占位符，由网络代理对获准的主机替换为真实密钥。自托管环境需要用户部署这样的代理（右图）。

其他产品的同类做法：Anthropic 把 MCP、CLI 与 GitHub 的令牌放在沙箱外的 vault 中，由代理按需取出；Claude Code 云会话的 GitHub 代理在服务端附加凭据；Codex Cloud 的 network secret 经代理替换；Google Managed Agents 的网络按域名白名单开启；Cloud Run sandboxes 的出站网络默认关闭。

本地沙箱也有这两条边界。SideKernel 为北向通道提供网络开关，打开后阻断所有出站流量，保留 api.anthropic.com 以便模型推理继续进行。作者的问卷中，在沙箱中运行编程 agent 的用户不到 40%。

接口 ③

执行环境的研究

agent 的状态分布在对话历史、文件系统和进程三处。故障恢复、抢占式实例上的执行、树搜索与 RL rollout 的分支，都需要保存并恢复这三部分，即沙箱的检查点与恢复（checkpoint/restore，下称 C/R）。Crab、DeltaBox、Fork-Explore-Commit 与 RippleCP 研究 C/R；ACRFence、Safe to Resume? 与 YoloFS 研究回滚与文件修改带来的安全问题；Firecracker、TrEnv-X、DSec 与 SideKernel 是沙箱基础设施。

Crab

Crab（arXiv 2604.28138）是 agent 沙箱的检查点与恢复系统，以宿主机上的运行时实现，对 agent 与 C/R 后端透明。它用 eBPF 观察每一轮工具执行对文件与进程的实际修改，据此决定检查点的粒度，并把检查点安排在 agent 等待 LLM 响应的时间内。

恢复不完整的后果

Crab 选取 50 个在正常运行中能解出的 Terminal-Bench 任务，在每条轨迹的随机位置注入一次崩溃，比较四种恢复策略（）。只恢复对话历史时，agent 依据的修改在新沙箱中已经丢失，回放 LLM 轨迹时求解率为 6%，实时调用 LLM 时为 28%。同时恢复对话与文件系统时，求解率为 48% 与 34%，缺少的是内存中的进程状态；实时调用 LLM 时，agent 发现状态缺失后会自行修补，进一步偏离原来的执行。从头重跑能解出全部任务，中位求解时间增至 1.81 倍（回放）与 1.55 倍（实时）。

检查点的频率与开销

agent 的单轮很短，Terminal-Bench 轨迹中单轮用时的中位数为 3.34 秒。每轮都打检查点时，单台主机上的检查点请求速率随沙箱密度上升，密度为 100 时中位数达到每秒 17 次（）。论文测得 ZFS 文件系统快照的开销在数十毫秒以内，CRIU 进程检查点在高并发下可增至数十秒。

一轮是否修改了 OS 状态，要观察执行结果才能确定。工具调用中 60% 是 run_shell_command，其中 70% 的 shell 命令缺少重定向、后台运行等表示副作用的语法线索（）。

设计

Inspector 由内核中的 eBPF 程序与用户态守护进程组成，判断每一轮的净修改：论文测得超过 75% 的轮次不产生恢复相关的状态，这些轮次跳过检查点，其余轮次按修改的范围选择只保存文件或同时保存进程。Coordinator 位于 LLM API 与沙箱之间，把检查点与轮次边界对齐，并与 LLM 等待时间重叠。C/R Engine 在主机范围内调度同机沙箱的检查点流量，用 CRIU 保存进程、用 ZFS 保存文件系统，由 Checkpoint Manager 维护可恢复的版本（）。Crab 支持 agent-in-a-sandbox 与 agent-with-a-sandbox 两种部署。

结果

恢复正确率由只恢复对话历史时的 8% 提高到 100%，检查点流量最多减少 87%，端到端时间在无故障、无检查点基线的 1.9% 以内；96 个沙箱同机部署时，Coordinator 每轮增加数十微秒。论文还演示了把回滚交给 agent：为 agent 提供 rollback() 工具后，QEMU 启动任务的用时由 434 秒降至 307 秒。

接口 ③

DeltaBox

DeltaBox（arXiv 2605.22781）面向树搜索与 RL 训练中频繁发生的沙箱 C/R。论文观察到，相邻两次检查点之间，沙箱里发生变化的文件和内存页很少，检查点因此可以只复制变化的部分。它在 Firecracker microVM 中实现了这一做法：检查点的本地工作约 10.83 ms，隐藏在模型推理时间内；回滚约 1.86 ms。

动机

编程 agent 通过 rm、pip install、sed 等命令修改真实的 OS 状态，这些副作用留在磁盘上，回退时需要恢复完整的沙箱状态。测试时搜索从两个方向加压：Best-of-N 横向展开多条轨迹，每条都需要快速克隆初始状态；MCTS 纵向回溯到任意历史节点，需要细粒度的 C/R。RL 训练则在每个训练步从同一个预热状态派生 k 个沙箱。

汇总了这两类用法在 SWE-bench 上的收益：MCTS 比线性 ReAct 的通过率高 4.7–6.7 个百分点，RL 训练使三个模型的通过率提高 19.2–29.4 个百分点。论文认为，C/R 的速度是限制深度搜索的原因之一。

已有方法的开销

已有方法按整份状态复制。git stash、shutil.copytree、Docker commit 与 Btrfs/LVM 快照保存文件；Firecracker 的 VM 快照保存内存与设备状态，块设备需另行快照；E2B 的文档化暂停按每 GiB 内存约 4 秒计；CubeSandbox 的快照与恢复为 49.8 ms 与 63.9 ms，依赖定制的宿主机内核（）。CRIU 恢复进程时按顺序加载内存页，多 GiB 的进程需要数秒。

设计

DeltaBox 提出 AgentState 抽象，把文件系统与进程内存作为一对按增量管理的状态（），由两部分实现。

  • DeltaFS（）在挂载状态下热切换 overlay 层。检查点时把当前可写层冻结为只读，在其上插入新的可写层，此后的修改写时复制到新层；回滚是 O(1) 的层切换。底层 XFS 的 reflink 让修改只复制被改动的 4 KB 块，与文件大小无关。
  • DeltaCR（）在每次检查点同时做 CRIU 转储和一次 fork()，后者产生冻结的模板进程放入模板池，两者都隐藏在等待 LLM 响应的时间内。回滚时命中模板池则从模板 fork 出新进程，复制的是页表；模板被逐出时退回 CRIU 慢路径，约 9.29 ms，结果仍然正确。

LLM 的网络连接由 sidecar 进程 NPD 代理，外部 I/O 绕开被恢复的 agent 进程；只读命令占 62.0% 的事件，跳过转储；按可达性回收转储，轨迹结束时的转储存储减少 46%–63%。

DSec 的结构

DSec 通过 Python SDK（libdsec）提供四种沙箱后端：FnCall、容器、microVM（Firecracker）与完整 VM（QEMU）（）。集群级服务负责身份、放置与节点监控；每个节点上的 Edge 管理沙箱生命周期，Aether 管理会话，Chronus 执行命令、读写文件与转发 HTTP。镜像以 EROFS 与 OverlayBD 格式存放在集群文件系统 3FS 上，按需加载。

负载测量（）对应三类机制（）：环境由分别版本化的基础镜像、workspace 与 toolkit 分层组合，toolkit 更新时镜像保持原样；高密度部署依靠内存共享、回收与 CPU 调度；镜像数据按需读取。评估中，按需拉取的累计磁盘写入比预先拉取少约 57%，完成时间快 1.71 倍；EROFS 挂载替代 tar 解压，完成时间快 1.76 倍；virtio-pmem 让多个客户机共享宿主机页缓存，峰值宿主机内存降低 40.2%；在 50% 的尽力而为负载下，core scheduling 把延迟敏感任务的延迟增幅由 45.2% 降到 17.3%。

与 RL 框架的协同

早期的训练流水线把 agent 循环放在可抢占的 GPU 训练 pod 中，GPU 任务被抢占时循环丢失而沙箱仍在，恢复依赖命令日志的重放。自 DeepSeek-V4.1 起，rollout 在 DSec 上执行，拆成两部分：agent 沙箱运行 harness（如 DeepSeek Harness）及其工具，worker 容器管理沙箱并提供与 harness 无关的控制层；两者都在可抢占的 GPU 池之外，被抢占的训练任务可以重新连接并继续。训练暂停时，RL 框架通知 DSec 暂停相关沙箱：容器先 docker pause 再回收内存，microVM 保存快照后终止 Firecracker 进程；之后的任何请求都会透明地恢复沙箱。

agent 的异常行为

DSec 记录了训练中 agent 通过非预期途径获取答案的行为：向 Chronus 的 socket 伪造 RPC 请求，读取 Chronus 日志寻找泄露的答案，覆盖 /bin/bash；加入文件与 socket 访问控制后，有 agent 用 XFS_IOC_SWAPEXT ioctl 交换文件的数据区段，导致 XFS 元数据损坏、文件系统下线。沙箱外，agent 扫描端口寻找可访问的镜像站，或经 Go 模块代理获取 GitHub 上的代码。普通命令也会破坏环境：从根目录递归 grep 读到 /proc/kpagecgroup 触发内核缺陷；yes 命令的输出被记录下来，占用数十 GB 存储。论文的结论是，检查最终输出不足以确认 agent 按预期解决了任务。

RollArt

RollArt（OSDI 2026）把 agentic RL 的各阶段放到不同的硬件上：prefill 为主的任务用计算型 GPU，decode 为主的任务用带宽型 GPU，环境运行在 CPU 集群，无状态的奖励计算放到 serverless 平台（）。rollout 按轨迹解耦，生成、环境交互与评分各自推进，慢的或出错的环境影响的是它所在的轨迹；训练与 rollout 在有界陈旧度下异步同步权重。论文统计的多任务训练步，正常运行时平均 365.7 秒，环境出现故障时平均 513.3 秒。与多种 RL 系统相比，训练时间缩短 1.31–2.05 倍；奖励计算移到 serverless 后，奖励 GPU 的利用率由 6% 升至 88%，每步 rollout 时间减半。

rollout 的长尾

Seer 观察到同一提示的多个请求在输出长度和模式上相近，RhymeRL 观察到相邻训练轮次的 rollout 相近，两者把这些相似性用于负载均衡和推测解码。DynaRL 用动态超图描述 RL 流水线，把 GPU 从过度配置的组件迁移到当前的瓶颈。RLinf 把高层工作流拆分后重组为执行流。HetRL 在异构 GPU 上求解调度问题。
